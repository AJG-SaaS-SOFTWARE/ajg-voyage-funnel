# Retry session failures after publication — 20 October 2026

## Change and boundary
The existing retry button awaited getSession outside a catch and silently did nothing for a missing client/session/token. A failure could escape the UI handler and leave a previous healthy diagnosis visible. The button now calls a reviewed named handler: invalidate prior reads, set checking/clear old evidence before the session preflight, catch client/session failures, reject the SDK error result or missing site/token, and delegate to the already-validated GET reader from #557 only if this is still the latest operation. Late older session success/failure cannot overwrite or start an outdated diagnostic after a newer operation. No automatic retry and no new authorization logic.

The existing getSession call is retained; server authentication and ownership checks remain authoritative. The Supabase skill security checklist and current official getSession documentation were consulted (https://supabase.com/docs/reference/javascript/auth-getsession). Markdown changelog retrieval was unsupported, so the HTML changelog was read instead. No SDK upgrade, auth configuration, session/cookie storage or privilege policy is changed.
